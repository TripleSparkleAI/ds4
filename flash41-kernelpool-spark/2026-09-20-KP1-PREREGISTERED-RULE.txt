THE QUESTION THIS ROUND ASKS
  P1, in the navigator's words: does the CUDA header change move CUDA decode at all?
  The census (CENSUS_pr1073_*.md) found that on the CUDA path every fused Metal entry is either
  a composition of the ops main already ran (op count unchanged) or returns 0 so ds4.c runs the
  unfused chain. So the header itself is predicted to move nothing. What CAN move CUDA decode
  are two ENGINE-GENERIC commits that are not about Metal at all:
    (a) 2a281b080: queue_layers becomes true for a single-node non-resident decode. On CUDA
        ds4_gpu_end_commands and ds4_gpu_flush_commands are both cudaDeviceSynchronize. Main
        drains after EVERY layer (~60 syncs/token); the PR at its default flush of 2 layers
        syncs after layer 0 and every second layer (~31 syncs/token). The host-side encode of
        the next layer's launches cannot overlap a sync, so each removed sync returns its
        bubble (launch latency + the host's encode time for one layer).
    (b) e76839617: at (n_comp + 7) / 8 <= 2048 blocks the two candidate-selection launches per
        index-source layer per token are skipped. At 4096 and 6144 tokens this applies.
  layer_resident = g->streaming && g->quality; the bench runs --ssd-streaming without --quality,
  so layer_resident is false and (a) is live in this regime. Read the arm's own log for the
  DS4_METAL_V41_DECODE_FLUSH_LAYERS default (unset -> 2) rather than assuming it.
